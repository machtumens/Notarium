## How This File Works (the `all-*.md` Convention)

Every `process/context/` directory has one `all-*.md` entrypoint that acts as an attachable quick router for that domain. This root file (`all-context.md`) is the top-level router. Context groups each have their own `all-{group}.md` entrypoint.

**The pattern:**

```
process/context/
  all-context.md                      <-- THIS FILE: root router
  planning/
    all-planning.md                   <-- group router for planning
    example-simple-prd.md             <-- deep doc within the group
    example-complex-prd.md            <-- deep doc within the group
  tests/
    all-tests.md                      <-- group router for tests
    debugging-and-pitfalls.md         <-- deep doc within the group
    e2e-tests.md                      <-- deep doc within the group
  database/
    all-database.md                   <-- group router for database
    schema-guide.md                   <-- deep doc within the group
    migration-procedures.md           <-- deep doc within the group
```

**How agents use it:**

1. Agent reads `all-context.md` first (this file)
2. Finds the relevant context group from the routing tables below
3. Reads that group's `all-{group}.md` entrypoint
4. Only then loads the specific deep doc needed

This layered routing keeps context windows small. Never load the whole `process/context/` tree.

**What each `all-{group}.md` must contain:**

- Scope (what the group covers and does NOT cover)
- Read-when rules (when an agent should load this group)
- Quick procedures or decision rules
- Source paths (list of deeper docs in the group)
- Update triggers (when to refresh this group's content)
- Routing to deeper docs within the group

## Context Group Lifecycle

Context groups are durable knowledge domains, not feature folders.

Create a group when:

- a topic has 3+ durable docs
- a single doc exceeds roughly 800 lines with separable subtopics
- multiple agents repeatedly need only one slice of a large context file
- the topic maps to a stable operational domain (tests, infra, database, auth, UI, workflows, etc.)

Do not create a group when:

- the content is a temporary report
- the content is a plan or execution artifact
- the topic is feature-specific and belongs in `process/features/...`

Move or split one group at a time. Use `all-{group}.md` entrypoints. Run the `audit-context` skill after every context organization change.

## Naming Convention

There are no `README.md` files inside `process/context/`.

Canonical entrypoints use `all-*.md`:

- root: `process/context/all-context.md`
- group: `process/context/{group}/all-{group}.md`

Each `all-{group}.md` file should act as the attachable quick router for that domain:

- tell the agent what the group covers
- give quick procedures and decision rules
- route to smaller deeper files

## Context Update Protocol

When durable project knowledge changes:

1. update the smallest relevant context file
2. update this file if routing, ownership, naming, or groups changed
3. update the owning `all-{group}.md` entrypoint when a group exists
4. run `audit-context`

## Key Patterns and Conventions

### Import aliases

- `@/` maps to `./src/` (configured in `vite.config.ts` `resolve.alias` and `tsconfig.json` `paths`).
- No backend aliases — backend uses relative imports throughout.

### Frontend routing

Two-layer routing pattern:

1. **URL routes** (`src/app/AppRoutes.tsx`): standard `react-router-dom` v6 `<Routes>/<Route>` with `<Suspense>` wrapper. Authenticated routes are wrapped in `<ProtectedRoute>`, admin in `<AdminRoute>`, ops in `<OpsRoute>`.
2. **Tab-state within the home shell** (`src/app/HomePage.tsx`): `currentPage` state drives which "page" component renders inside the shell without URL change. States: `'subjects' | 'subject-notes' | 'leaderboard' | 'chat' | 'admin' | 'ops'`. The `<ExpandableTabs>` component (bottom nav) toggles this state. **Important for Paperloop reframe**: the study/review flow uses a proper URL route (`/review`) but the main discovery shell still uses tab-state.

**Lazy loading:** nearly every page is code-split via `React.lazy()` in `src/app/lazyPages.ts`. New pages must be added there and imported lazily in `AppRoutes.tsx` or `HomePage.tsx`.

### Backend route structure

There is no framework (no Hono, no itty-router). `backend/src/index.ts` is a single giant `fetch` handler with manual `if (url.pathname.startsWith('/api/...'))` routing. Route handler functions are imported from `backend/src/routes/*.ts` and called directly.

Pattern for adding a new route:

1. Write the handler function in the relevant `backend/src/routes/*.ts` file.
2. Import and call it inside the `switch`/`if` block in `backend/src/index.ts`.

### Authentication pattern

- **JWT (24h expiry)**: issued at login, stored in `sessionStorage` under key `notarium_token`. Bearer token on every API request.
- **Refresh tokens (7d)**: stored in D1 `refresh_tokens` table. Rotated on use.
- **Admin auth**: separate `ADMIN_PASSWORD` env secret checked against a fixed hash; admin users have `role = 'admin'` in D1.
- **2FA**: TOTP (`backend/src/lib/totp.ts`), backup codes stored in `users.totp_backup_codes`.
- **Google OAuth**: PKCE flow, tokens encrypted with `OAUTH_TOKEN_AES_KEY` before storage in `oauth_tokens` table.
- **Rate limiting**: `checkRateLimit()` tries `RATE_LIMITER` Durable Object first (atomic), falls back to KV sliding-window. Rate limit window: 900s, max 5 attempts per window.

### API client pattern

`src/lib/api.ts` exports a singleton `api` object with a typed `.request<T>(path, options)` method. Base URL auto-detected: `http://localhost:8787` in development, `VITE_API_URL` env var (or hardcoded workers.dev URL) in production.

### State management

No global state library. Auth state lives in `src/app/AuthContext.ts` (React context). Study feature state is local to each hook (`useStudyFeatures`, `useNoteInteractions`). No Redux, no Zustand.

### Error handling

- Backend: `jsonResponse()` helper from `backend/src/lib/response.ts` wraps all responses with CORS headers. Errors are returned as `{ error: "message" }` JSON.
- Frontend: errors surfaced via `sonner` toast notifications (`toast.error(...)`). API errors throw; components catch with try/catch.

### Naming conventions

- Files: camelCase for hooks/utilities, PascalCase for components and pages.
- TypeScript: PascalCase interfaces/types, camelCase variables/functions, `UPPER_SNAKE_CASE` for env-level constants.
- Backend route files: lowercase (`notes.ts`, `study.ts`, `ai.ts`).
- Test files: collocated in `__tests__/` subdirectories next to the module they test.

### SM-2 Spaced Repetition Engine

Located in `backend/src/routes/study.ts`. Key function: `computeSm2(prev: Sm2State, quality: number): Sm2Result`.

- Quality mapped from `(isCorrect, confidence)` via `toQuality()`: wrong = 2, correct+low = 3, correct+medium = 4, correct+high = 5.
- SM-2 standard formula: ease factor floors at 1.3, interval doubles on success, resets to 1 day on failure.
- Items stored in `study_items` table with `ease_factor`, `interval_days`, `repetitions`, `due_at`.
- Each correct answer awards `learning_points` to the user (`POINTS_CORRECT = 10`, `POINTS_CONFIDENCE_BONUS = 5`).
- `updateStreak()` updates `current_streak`, `longest_streak`, `last_study_date` on every answer.

### AI primitives

Located in `backend/src/routes/ai.ts`:

- `performOCR` — calls Google Cloud Vision API to extract text from uploaded note photos.
- `generateNoteSummary` — calls Gemini to summarize note content.
- `generateQuiz` — calls Gemini to generate quiz questions from a note.
- `explainConcept` — calls Gemini to explain a specific concept from a note.
- `generateStudyPlan` — calls Gemini to create a study plan.
- `chatWithGemini` — multi-turn chat with the user's notes injected as context (RAG-style, up to 10 notes, 1200 chars each).
- All AI usage is logged to the `ai_usage` D1 table (provider, endpoint, ok, duration_ms, tokens).

**Paperloop-relevant column confirmation:**

- `users.learning_points` — EXISTS (INTEGER DEFAULT 0). Updated on every correct SM-2 answer.
- `users.current_streak` — EXISTS (INTEGER DEFAULT 0). Updated daily on study session.
- `users.longest_streak` — EXISTS (INTEGER DEFAULT 0).
- `users.last_study_date` — EXISTS (TEXT). Used for streak continuity check.
- `users.total_likes` — EXISTS. Used in current leaderboard formula alongside `notes_uploaded` and `total_admin_upvotes`.
